# 项目组件化

1. 本质就是分层思想，业务组件形成业务层，通用组件形成通用层，组件间没有依赖关系，但是业务组件可以向下依赖通用组件。
2. 然后把各个组件包成库的形式用pod进行依赖管理。
3. 业务组件间的调度通过一个中间件进行，中间件一般也看成路由，实现上可以通过URL、协议等，也就是B向中间间注册，A通过中间件调用的逻辑。

1. 基础功能组件（独立于app）：
按功能分库，不涉及产品业务需求，跟库Library类似，通过良好的接口拱上层业务组件调用；不写入产品定制逻辑，通过扩展接口完成定制； 
2. 基础UI组件（独立于app）：
各个业务模块依赖使用，但需要保持好定制扩展的设计 。
3. 业务组件：
业务功能间相对独立，相互间没有Model共享的依赖，业务之间的页面调用只能通过UIBus进行跳转，业务之间的逻辑Action调用只能通过服务提供。
4. 中间件：
URL路由、target-action，protocol-class


# 中间件的处理
### URL 路由
基于 URL 匹配的，或者是根据命名约定，用 runtime 方法进行动态调用。它在跨平台路由管理上的确是最适合的方案，也是目前使用最多的[CTMediator](https://zhuanlan.zhihu.com/p/272599900)。
优点：
	* 极高的动态性，适合经常开展运营活动的 app，例如电商
	* 方便地统一管理多平台的路由规则
	* 易于适配 URL Scheme
缺点：
	* 硬编码
	* 违背开闭原则，新增或者变化url时，要在具体模块内进行修改支持。
原理：
	 * runtime通过字符串拿到一个类，然后字符串转化为sel，然后做执行。

> 针对URL 路由可以通过类似工厂方法的处理思想，通过中间抽象类来处理变化部分，模块实现接口即可，达到松耦合的目的，模块内无需修改。
